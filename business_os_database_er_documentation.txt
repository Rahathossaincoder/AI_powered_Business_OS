================================================================================
BUSINESS OS - COMPLETE DATABASE / ER DIAGRAM DOCUMENTATION
================================================================================

Purpose:
This document defines the Phase 1 database entities, attributes, relationships,
constraints, and ER-diagram drawing instructions for the Business OS MVP.

MVP SCOPE
---------
1. Multi-tenant organizations
2. Authentication
3. Users and employees
4. Roles and permissions
5. Product catalog
6. Inventory and inventory ledger
7. Customers / CRM
8. Orders and checkout
9. Payments
10. Invoices and receipts
11. Dashboard/reporting data
12. Read-only AI chatbot
13. AI conversations and tool calls
14. Notifications
15. Organization settings
16. Audit logging

AI SCOPE FOR MVP
-----------------
The AI is a chatbot only.

It is READ-ONLY in the MVP.
It can query business information through controlled backend tools.

It must NOT:
- create orders
- modify inventory
- create products
- delete customers
- modify employees
- modify organization settings
- execute arbitrary SQL

The AI uses business-level read tools such as:
- get_sales_summary
- get_sales_by_period
- get_revenue_trend
- get_top_products
- get_product_sales
- get_inventory_summary
- get_low_stock_products
- get_customer_summary
- get_top_customers
- get_order_summary
- get_orders_by_status

================================================================================
1. ER DIAGRAM SYMBOLS
================================================================================

[Single Rectangle] = Strong Entity
[Double Rectangle] = Weak / Associative Entity
(PK, Underlined) = Primary Key
(FK, Underlined with dotted line) = Foreign Key
(FK, Unique) = Foreign Key + Unique
(Simple) = Simple Attribute
(Derived, Dotted underline) = Derived Attribute
(Alternate Key) = Unique / Alternate Key
═══ = Total Participation
─── = Partial Participation
◇ = Relationship
◆ = Identifying Relationship

For implementation, every organization-owned entity must contain
organization_id and must be tenant-scoped by the backend.

24. DATABASE-WIDE IMPORTANT CONSTRAINTS
================================================================================

1. Tenant isolation
   -----------------
   Every organization-owned record must be scoped by organization_id.

2. Backend determines tenant
   --------------------------
   Never trust organization_id supplied by the frontend.

3. Product SKU
   ------------
   UNIQUE(organization_id, sku)

4. Employee code
   --------------
   UNIQUE(organization_id, employee_code)

5. Customer code
   --------------
   UNIQUE(organization_id, customer_code)

6. Order number
   -------------
   UNIQUE(organization_id, order_number)

7. Invoice number
   ---------------
   UNIQUE(organization_id, invoice_number)

8. Receipt number
   ---------------
   UNIQUE(organization_id, receipt_number)

9. Organization setting
   --------------------
   UNIQUE(organization_id, key)

10. Role permission
    ----------------
    UNIQUE(role_id, permission_id)

11. Inventory
    ---------
    One inventory record per product:
    UNIQUE(product_id)

12. Invoice
    -------
    One invoice per order in MVP:
    UNIQUE(order_id)

13. Receipt
    -------
    One receipt record per invoice in MVP:
    UNIQUE(invoice_id)

14. Payment
    --------
    Multiple payments per order are allowed.

15. Order item price
    -----------------
    unit_price is stored historically on OrderItem.

16. Inventory ledger
    -----------------
    Every stock-changing operation must create an
    InventoryTransaction.

17. AI access
    ----------
    AI has read-only tools in MVP.

18. Arbitrary SQL
    --------------
    AI must NOT receive arbitrary database execution privileges.

25. IMPORTANT BUSINESS RULES
================================================================================

ORDER COMPLETION
----------------

Complete Order must happen transactionally:

  1. Validate order
  2. Validate product availability
  3. Validate stock
  4. Create Order
  5. Create OrderItems
  6. Update Inventory
  7. Create InventoryTransactions
  8. Create Invoice
  9. Create payment record if applicable
 10. Queue receipt/PDF generation
 11. Write AuditLog


INVENTORY
---------

When stock changes:

  quantity_before
        +
  quantity_change
        =
  quantity_after

Never silently modify stock without an inventory transaction.


AI
--

The AI does not directly access the database.

Flow:

  User
    ↓
  Chat UI
    ↓
  AI Gateway
    ↓
  Local LLM
    ↓
  Read-only business tool
    ↓
  Business Service
    ↓
  Tenant-scoped query
    ↓
  PostgreSQL
    ↓
  Structured result
    ↓
  LLM
    ↓
  User

36. IMPORTANT DESIGN PRINCIPLE
================================================================================

The database is the source of truth.

Business logic belongs in backend services.

The AI is a consumer of read-only business services.

The dependency direction should be:

    Frontend
       ↓
    Backend API
       ↓
    Business Services
       ↓
    PostgreSQL

AI:

    Chat UI
       ↓
    AI Gateway
       ↓
    Local LLM
       ↓
    Read-only Business Tools
       ↓
    Business Services
       ↓
    PostgreSQL

Do NOT build:

    AI → arbitrary SQL → PostgreSQL

Build:

    AI → controlled tool → business service → tenant-scoped query
